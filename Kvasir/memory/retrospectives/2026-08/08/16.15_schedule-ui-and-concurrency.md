## Key Code Changes

The Schedule form now stores a maximum profile count separately from the number allowed to run at once. A value above one selects parallel execution; one keeps sequential behavior. The browser updates its warning while the user edits the fields and blocks invalid submission. The route normalizes the numeric value and rejects invalid configurations before persistence. The scheduler keeps the configured concurrency when it converts a scheduled profile count into a runnable batch, while the existing worker logic naturally handles a final partial round.

The Schedule row now has three layout regions: summary, history, and actions. History has a bounded vertical size and its own overflow behavior. The action group contains all three controls and prevents buttons from stretching to match history content. On narrow screens the regions collapse in a readable order.

## Architecture Decisions

- Keep profile_count as the total requested profile count and use max_concurrency only for simultaneous work.
- Derive execution_mode from concurrency for Schedule-created batches rather than adding another redundant Schedule toggle.
- Enforce the upper bound in both browser validation and server validation.
- Keep history in the same Schedule row but isolate it from the action controls with a dedicated grid column.
- Leave unrelated existing untracked documentation outside the commits.

## Honest Feedback

Three friction points stood out. First, the visual layout problem was not fully apparent from static source inspection because the grid allowed content inside one label to affect the perceived row alignment. Second, the Schedule history and controls were initially modeled as one flex group, which made the button stretching behavior easy to miss until there were enough history entries. Third, the remote branch advanced between pushes during the earlier work, requiring a fetch and rebase before the first push could complete. These were resolved safely, but they suggest a better default workflow: inspect the rendered structure whenever a request is specifically about alignment, isolate variable-height content from controls, and verify remote ancestry immediately before pushing. The test suite was strong for behavior, but it did not replace a quick visual check for layout details.

## Lessons Learned

- Variable-height content should not share a flex or grid item with fixed action controls.
- Paired form inputs should have an explicit shared row contract when visual alignment matters.
- A concurrency setting needs both a total-count invariant and a worker-limit invariant.
- Browser feedback and server validation should express the same rule in different layers.
